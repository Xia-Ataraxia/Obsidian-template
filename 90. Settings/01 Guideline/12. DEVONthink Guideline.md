## Waypoint

- **Scope**: DEVONthink 개인 데이터베이스의 독립형 PARA 아카이브 역할 정의, 구조, 캡처 라우팅, MCP 운영 규칙을 정의한다.
- **Siblings**: [[04. Applications and Integrations]] (도구 역할 + 캡처 라우팅)
- **Out of scope**: Obsidian vault 구조 (→ [[01. Folders and Placement]]), Zotero 구조, 동기화·백업 메커니즘
- **Review trigger**: DEVONthink 역할이 90 일간 안정적이면 도구 개요로 재흡수 후보 (일관성 비용 완화).

## Overview

DEVONthink 은 Obsidian / Zotero 의 실시간 인덱스가 아니라 **독립형 PARA 아카이브**다. 캡처 라우팅의 "reference / archive" 종착지로서, 자체 PARA 1-depth 구조(`10 Projects / 20 Areas / 30 Resources / 40 Archives`)로 운영된다. `60. Saint` 는 신앙을 삶의 근간으로 두는 1급 non-PARA 최상위 예외다.

과거의 "다른 도구를 인덱싱" 역할은 폐기되었다. 실시간 인덱스가 아니어서 생기던 마찰과 인지 비용을 제거하고, DEVONthink 을 그 자체로 완결된 자료 보관소로 재정립한다.

## Map

### 구조 (Confirmed Top-level)

```
00. Inbox       — 캡처
10. Projects    — 마감 있는 능동 목표
20. Areas       — 유지할 책임 영역
30. Resources   — 관심사 허브 (80. References + 70. Collections 점진 편입)
40. Archives    — 비활성 (연도 폴딩 유지)
60. Saint       — 신앙, 1급 예외, non-PARA
```

material-class(Library / Web / Records / Media)는 미리 만들지 않는다 — `30. Resources` 하위 그룹이나 태그로 필요가 생길 때 점진적으로 성장시킨다.

### 축 규칙 (Axis Rules)

DEVONthink 의 1-depth 는 PARA *패턴*을 따른다. 이는 Obsidian 의 subject-decimal 최상위(`10. Time / 30. Literature Notes / 40. Permanent Notes …`)의 복제가 아니다.

- Obsidian = note-type + PARA 축
- DEVONthink = project-status / archive 축

cross-tool 연결은 folder parallelism 이 아닌 **identifier** 로 한다 (DEVONthink UUID / Zotero citekey / Eagle item ID).

### 캡처 라우팅 (into DEVONthink)

캡처 트리에서 "Reference / archive" 종착지로 도달한 콘텐츠를 DEVONthink `00. Inbox` 로 임포트한다. Inbox 에서 PARA bucket 으로 분류한 뒤 이동한다. 도구 역할과 캡처 라우팅의 정본은 [[04. Applications and Integrations]] 다.

### 태그 & 연결

- 주제 분류 = 태그 (DEVONthink tag, group hierarchy 아님)
- cross-tool 연결 = 필요한 노트 본문에만 DEVONthink deep link(`x-devonthink-item://UUID`). frontmatter 에 `dt_uuid` 를 저장하지 않는다 — 두 시스템의 레코드 집합을 맞추려는 시도가 인덱싱과 같은 결합을 만든다. 그 외 외부 도구는 기존 식별자를 쓴다 — citekey(Zotero), item ID(Eagle)
- Smart Group 및 특수 그룹(Trash, Tags, Duplicates)은 운영 중 수정하지 않는다

## Rules

- DEVONthink 을 standalone PARA 아카이브로 운영한다 — Obsidian / Zotero 의 인덱스 역할이 아니다.
- 모든 DEVONthink 조작(rename / move / trash / create)은 MCP 경유 또는 AppleScript fallback 으로 한다. `.dtBase2` 파일시스템 직접 수정 금지.
- 모든 batch 조작(move_record / trash_record / update_record)은 dry-run 목록 → 명시 확인 → 실행 순서를 지킨다. 확인 없는 mutation 금지.
- `30. Resources` 의 하위 그룹 및 태그는 필요가 생길 때 생성한다 (선제적 빈 그룹 생성 금지).
- `60. Saint` 는 PARA 범주 밖의 1급 최상위 그룹으로 유지한다. 편입하거나 번호를 PARA 범위(10–40)로 옮기지 않는다.
- MCP batch 상한: move_record / update_record / trash_record 각 ≤ 500 uuid/call.

## Caveats

### PARA 패턴 ≠ Obsidian 구조 복제

DT 의 `10 Projects / 20 Areas / 30 Resources / 40 Archives` 는 PARA 패턴을 1-depth 에 적용한 것이다. Obsidian vault 의 `NN. Name/` subject-decimal 구조를 복사한 것이 아니다. 두 시스템의 top-level 번호가 겹쳐도 우연의 일치이며 연결 고리가 아니다. Obsidian ↔ DEVONthink 연결은 identifier(UUID)로만 허용한다.

### 빈 그룹 누적 방지

프로젝트 / 영역이 종료되면 해당 그룹을 `40. Archives` 로 이동하거나 trash 처리한다. 빈 그룹을 무기한 잔류시키지 않는다. 정기 점검: `get_group_tree` → 빈 그룹 식별 → dry-run → 확인 → trash.

### MCP 안전 운영

DEVONthink MCP 의 `move_record`, `trash_record`, `update_record` 는 batch 로 작동하며 즉시 DB 를 수정한다. 항상 `get_group_tree` / `get_record_children` 로 사전 상태를 확인한 뒤 조작하고, 작업 후 동일 도구로 사후 상태를 검증한다. 시스템 그룹 제외는 이름이 아닌 type(kind) 기반으로 한다 (로컬라이즈된 이름 매칭의 silent fail 회피).
