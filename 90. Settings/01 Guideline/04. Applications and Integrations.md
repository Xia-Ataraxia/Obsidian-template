## Overview

This guideline defines the roles and configuration boundaries of applications, services, integrations, and plugins used by the vault.

- **Covers**
	- application and service roles, interfaces, and data locations
	- plugin installation evidence and plugin-managed properties
	- Obsidian Sync and Git role separation, plus configuration checks after folder changes
- **Does not cover**
	- template authoring, placement, or engine configuration (see [[15. Templates]])
	- agent authority or workflow selection (see [[03. Agent Permissions and Workflows]])
	- runtime installation, authentication, configuration, update, or recovery (outside this template's scope; belong to the adopter's infrastructure notes)
- **Authoring**
	- Follow [[00. Guideline Authoring]] and [[guideline.template]].

```text
Applications and Integrations
├── Plugin Philosophy — 최소 플러그인
├── Per-Plugin Reference — 설치 증거 vs community-plugins.json
├── Plugin-managed Properties — 직접 수정 금지 목록
├── Linter Ignore Policy — yaml-timestamp 자동 관리
├── Application Roles — application and service roles
├── Interfaces and Distribution Units — GUI / CLI / API / MCP / skill / plugin
├── Capture Routing — 캡처물을 어느 도구로 보낼지
├── Do-NOT-mirror Rule — 타 도구에 Obsidian 폴더 패턴 이식 금지
├── Git and GitHub — 변경 이력과 저장소의 역할
└── .obsidian Sync Rules — taxonomy 변경 시 플러그인 설정 동기화
```

## Map

### Plugin Philosophy

- **최소 플러그인 원칙을 유지한다.**
	- vault 기능은 core Obsidian과 소수의 검증된 커뮤니티 플러그인으로 유지한다.
	- 새 플러그인 도입 전 기존 플러그인으로 대체 가능한지 먼저 확인한다.
	- 유지보수가 끊겼거나 기능이 core Obsidian으로 흡수된 플러그인은 발견 즉시 제거한다.

### Per-Plugin Reference

- **설치와 설정을 구분한다.**
	- `.obsidian/community-plugins.json`의 ID 목록은 설정(활성 후보)이지 설치 증명이 아니다.
	- 설치는 `.obsidian/plugins/<id>/manifest.json` 존재로 확인한다.
	- 이 문서는 Obsidian 런타임 enable 여부를 GUI로 검증하지 않는다.
- **설치 상태를 역할 계약과 섞지 않는다.**
	- Templater·ZotLit의 엔진·템플릿 설정은 [[15. Templates]]가 담당한다.
	- 사용자 대면 hybrid 검색용 외부 `qmd` CLI와 QMD 플러그인을 혼동하지 않는다.
	- `plugins/<id>/manifest.json`이 없으면 그 플러그인에 의존하지 않는다.

- **Periodic Notes는 설치 전제로 쓰지 않는다.**
	- `auto/` 폴더를 설치 증거로 쓰지 않는다.
		- auto 템플릿 계약은 [[15. Templates]]를 따른다.

### Plugin-managed Properties

- **다음 접두어 property는 해당 플러그인이 자동 관리한다.**
	- `excalidraw-*`
	- `kanban-plugin`
	- `banner*`
	- `cards-deck`
	- 수동 편집 시 플러그인 상태와 어긋나 깨질 수 있다.

- **Reference Manager Properties는 Paper/Book 전용이다.**
	- 필드: `zotero`, `zt-attachments`, `bookends`
	- Zotero/ZotLit/Bookends가 채운다.
	- 파일 이동 시 이 값들이 에러 없이 깨질 수 있다.
	- 필드 스키마는 [[02. Properties]]가 담당한다.

### Linter Ignore Policy

- **`obsidian-linter`의 `yaml-timestamp` 규칙은 `date_created`/`date_modified`를 파일시스템 기준으로 자동 관리한다.**
	- 이 두 필드를 수동으로 편집해도 저장 시 덮어써질 수 있다.
	- 필드 의미는 [[02. Properties]]가 담당한다.

- **이 문서는 플러그인 설정 파일을 편집하지 않는다.**
	- ignore 키와 실제 값은 채택자의 `.obsidian/plugins/obsidian-linter/data.json`에서 확인한다.

### Application Roles

Responsibility—not human-vs-agent or internal-vs-external—is the organizing axis for application and service roles.

| 도구 | 역할 | 데이터 위치 |
|---|---|---|
| Obsidian | PKM 허브, 모든 노트의 중심 | 이 vault (워크스페이스 멤버 `Vault/`). 공유 안내는 vault-relative. |
| Zotero | 학술 인용 관리 | vault 밖 호스트 자산. 논리 이름 `Zotero`(라이브러리/DB)와 `Zotero-PDFs`(PDF 아카이브) |
| DEVONthink | 표준 참고자료 아카이브(standalone PARA) | vault 밖 호스트 자산 `DEVONthink` |
| Eagle | 이미지/비주얼 자산 관리(직교 축) | vault 밖 호스트 자산 `Eagle` |
| GitHub | Repository hosting and source/provenance identity; version and backup policy remains in [[#Git and GitHub]] | External repositories |

- **기계 home 경로는 이 문서에 하드코딩하지 않는다.**
	- Asset 표는 이 템플릿 범위 밖이며 채택자의 인프라 노트에 둔다.

### Interfaces and Distribution Units

These concepts describe how a capability is exposed or packaged; they do not create an authorization tier.

- **GUI** is an interactive application surface for a person or an agent using the application.
- **CLI** is a command-line interface for a supported runtime or service, usable by a person or an agent.
- **API** is a programmatic interface exposed by an application or service.
- **MCP** is a protocol. An MCP server exposes capabilities through that protocol; the server is an integration endpoint, not a skill.
- **Skill** is a procedure selected and loaded for a request. Selection belongs to [[03. Agent Permissions and Workflows]], while mechanics and dependencies belong to the skill source.
- **Plugin** is either an application extension or a runtime distribution unit. An Obsidian plugin extends Obsidian; a GJC plugin distributes runtime capabilities and installed skills. Installation evidence and plugin configuration boundaries belong here; a plugin is not a skill procedure.

### Capture Routing

자료를 별도로 수집·보관할 때 적용한다. 본문에서 외부 이미지·영상을 표시하는 방식은 [[05. Writing Style#Links & Evidence]]를 따르며, 임베드를 위해 파일을 수집하라는 뜻이 아니다.

```text
캡처물 판정
├── 인용 가치 있는 학술 자료 → Zotero
├── 깊이 읽을 대상(active queue) → 큐에 유지
├── 참고/아카이브용 → DEVONthink
└── 이미지(직교 축, 항상) → Eagle
```

### Do-NOT-mirror Rule

- **다른 도구에 Obsidian의 `NN. Name/` 폴더 패턴을 이식하지 않는다.**
	- 도구 간 링크는 식별자로만 연결한다.
	- 식별자는 Zotero citekey, DEVONthink UUID, Eagle item ID다.
	- DEVONthink 자체의 PARA 1-depth 구조는 예외다. 상세는 [[#DEVONthink PARA Exception]]을 본다.

### Vault Search

- **볼트 검색은 qmd의 `obsidian` collection을 사용한다.**
	- 사용자·에이전트 노트를 별도의 검색 collection으로 나누지 않는다.
	- 검색어를 전달할 때는 `qmd query --collection obsidian "검색어"`를 사용한다.
- **검색과 인덱스 갱신은 구분한다.**
	- `qmd update`·`qmd embed`는 사용자가 명시적으로 요청했을 때만 수동으로 실행한다.
	- 노트 편집이나 커밋을 이유로 인덱스를 자동 재구축하지 않는다.
	- 자동 갱신 hook의 설치·활성 여부는 해당 환경의 설정에서 확인한다. 가이드라인에 적혀 있다는 사실을 실행 보증으로 삼지 않는다.

### Git and GitHub

- **볼트의 기기 간 동기화는 Obsidian Sync가 담당한다.**
	- Git과 GitHub는 변경 이력 관리와 백업·복구에 사용한다.
	- Git push/pull을 볼트의 기기 간 동기화 수단으로 사용하지 않는다.
	- GitHub에 백업했다는 사실을 Obsidian Sync 완료로 간주하지 않는다.
	- 기기별 백업 저장소와 branch는 각 작업 사본의 이력을 보존한다.
		- 서로 맞추기 위해 remote를 바꾸거나 branch를 강제로 합치지 않는다.
		- 독립 저장소와 Obsidian Sync의 관계에 대한 추가 제약은 [[#Independent Backup Histories]]를 따른다.

- **노트와 운영 규칙의 버전은 Git commit history로 관리한다.**
	- 현행 파일을 수정하고 의미 있는 변경 단위로 커밋한다.
	- 무엇을 왜 바꿨는지 커밋 메시지에 남긴다.
	- 과거 버전 보존만을 위한 `_archive/`, 날짜별 사본, `old`·`backup` 노트를 만들지 않는다.
	- 폐기된 가이드라인은 Git에 보존된 상태를 확인한 뒤 현행 트리에서 제거한다.
		- 이전 내용은 해당 경로의 commit history에서 확인한다.
	- 완료된 업무를 모으는 Work Archive와 외부 원본 보존은 버전 사본이 아니므로 이 규칙으로 삭제하지 않는다.

- **Obsidian 노트 작업은 현재 브랜치에서 바로 커밋·푸시한다.**
	- 혼자 사용하는 볼트의 실시간 작성 흐름을 유지한다. 일반적인 노트 편집을 위해 브랜치를 전환하거나 별도 worktree를 만들지 않는다.
	- 해당 작업에서 바꾼 경로만 stage하고 검증한 뒤, 기존 remote와 작업 브랜치에 커밋·푸시한다.
		- `git add -- "경로"`로 대상만 stage한다.
		- `git add -A`, `git add .`, `git commit -a`는 사용하지 않는다.
		- 커밋 전에 `git status --short`와 `git diff --cached`로 stage 범위를 확인한다.
		- 에이전트는 완료를 보고하기 전에 task-owned 변경을 검증하고 커밋한다.
		- 의미 있는 파일 변경이 없으면 빈 커밋을 만들지 않는다.
		- 커밋 메시지 trailer에는 실제 실행 런타임을 `Agent: <runtime>`으로 기록한다.
			- 예시는 `Agent: GJC`다.
			- 공유된 Git author·committer identity는 사람·에이전트 여부나 노트의 `authorship: mixed`를 증명하지 않는다.
			- 정확한 provenance는 [[02. Properties#Authorship|작성 주체]]가 소유한다.
			- 실행하지 않은 정체성의 `Co-authored-by` trailer를 만들지 않고 git config를 바꾸지 않는다.
		- 완료 결과에는 실제 commit hash를 기록한다.
		- 커밋이 실패하면 파일 저장과 Git 기록 상태를 구분해 보고하고 버전 기록 완료로 처리하지 않는다.
		- 커밋 과정의 환경·신원·서명·hook·권한 예외는 [[#Agent Commit Failures]]에 모은다.
	- 승인된 파일 이동·삭제는 `git mv`·`git rm`으로 수행한다.
	- PR은 기본 절차가 아니다. 사용자가 해당 작업에 명시적으로 요청한 경우에만 사용한다.
	- 이 규칙은 볼트 작업에 적용한다. 외부 소프트웨어·skill 저장소의 브랜치·PR 정책을 바꾸거나 볼트에 그대로 가져오지 않는다.

- **사람이 읽는 세션 보고서의 `Verification`에는 작업 commit 증거를 남긴다.**
	- 해당 세션의 최종 작업 commit URL 하나만 남긴다.
		- 검증한 push remote와 full SHA로 만든 immutable URL을 사용한다.
		- 후속 작업 commit이 확인되면 기존 링크를 교체하며 이전 링크나 별도 SHA 목록을 누적하지 않는다.
		- 아직 커밋되지 않았으면 hash나 URL을 만들지 않고 미커밋 상태를 기록한다.
	- 게시 증거로 제시하기 전에 push remote와 원격 branch에 작업 SHA가 포함되는지를 확인한다.
		- push 성공과 원격 ref 또는 검증한 원격 이력을 근거로 사용한다.
	- source vault 이름, 실제 작업 사본 경로, 알려진 source machine, source repository URL, source branch를 기록한다.
		- 작업 경로는 `git rev-parse --show-toplevel`, branch는 `git branch --show-current`, push remote는 `git remote get-url --push <remote>`로 확인한다.
	- 원격 게시를 확인한 경우 publication status를 `confirmed`로 기록한다.
		- 로컬에만 커밋한 경우는 `local-only`로 기록한다.
		- 원격 상태를 확인하지 못한 경우는 `unverified`로 기록하며 게시됐다고 추정하지 않는다.
	- Obsidian Sync가 보고서를 복사해도 원래 source 정보와 게시 확인 근거를 보존한다.
		- 수신 machine으로 바꾸거나 backup commit만으로 authorship을 추론하지 않는다.
	- 같은 커밋의 hash를 보고서에 넣는 문제는 [[#Commit Evidence Self-reference]]를 따른다.

- **결정의 이유는 커밋에, 현재 유효한 규칙은 담당 지침에 남긴다.**
	- 별도 ADR 문서·번호·supersede 체인을 작성하도록 요구하지 않는다.
	- 변경 이유와 중요한 제약·대안은 커밋 메시지에 기록한다. 계속 적용될 규칙은 기존 담당 가이드라인에 반영한다.
	- 기존 ADR은 과거 결정의 근거다. 새 작성 절차를 사용하지 않는다는 이유로 과거 기록이나 그 기록의 인용을 일괄 삭제하지 않는다.

- **GitHub URL은 저장소의 책임을 식별하는 연결이다.**
	- 저장소마다 무엇을 관리하는지, 어느 작업 환경과 remote가 연결되는지, 기준 branch와 확인 근거를 함께 기록한다.
	- 같은 이름이나 계정에 있다는 이유만으로 같은 원본 저장소라고 추정하지 않는다.
	- 노트 내용은 이 볼트에서, 변경 이유와 이전 버전은 해당 저장소의 commit history에서 찾는다.

- **분산 환경에서는 작업 위치와 remote를 확인한다.**
	- 커밋·푸시 전에 현재 저장소, branch, fetch/push URL을 확인한다.
	- 이 작업의 변경만 stage하고 다른 사람의 변경을 포함하지 않는다.
	- push 충돌을 force push로 덮어쓰지 않는다.
		- 미커밋 변경을 보존하고 충돌을 해결한다.
		- push가 거절되면 rebase가 가능한 작업 트리에서 `git pull --rebase` 후 다시 검증하고 push한다.
		- 다른 작성자의 변경을 보존한 채 진행할 수 없거나 충돌이 생기면 임의로 stash·삭제하지 않고 보고한다.

### `.obsidian` Sync Rules

> [!important] 원칙: taxonomy 변경은 플러그인 설정 변경을 동반한다
> 폴더 rename/renumber/이동(`git mv`, 승인된 재분류 등)이 일어나면, 그 변경을 수행하는 주체가 같은 작업 배치 안에서 `.obsidian/plugins/**/data.json` 중 경로를 참조하는 설정을 감사하고 갱신한다. taxonomy와 플러그인 설정이 분리된 채 방치되면 spec gap이 누적된다.

- **감사 대상은 경로 키 존재 확인이다.**
	- 설치된 플러그인의 `data.json` 중 폴더 경로를 참조하는 키
	- Templater (`.obsidian/plugins/templater-obsidian/data.json`)
	- Templater 키의 의미는 [[15. Templates]]가 담당한다.
	- 설정 파일은 이 문서가 편집하지 않는다. 플러그인 설정 편집은 별도 작업이다.

## Rules

- 플러그인을 쓰기 전에 `.obsidian/plugins/<id>/manifest.json`으로 설치를, `community-plugins.json`으로 설정 ID를 따로 확인한다.
	- 새로 도입하려면 기존 플러그인으로 대체 가능한지 먼저 본다.
- property를 손대기 전에 [[#Plugin-managed Properties]] 목록을 확인한다.
- 도구를 연결하기 전에 citekey/UUID/item ID만 썼는지 확인한다.
	- Obsidian의 `NN. Name/` 패턴을 다른 도구에 이식하지 않았는지는 [[#Do-NOT-mirror Rule]]을 본다.
- taxonomy를 바꾼 같은 작업에서 `.obsidian/plugins/**/data.json`의 경로 키를 감사한다.
	- 대상 파일은 [[#.obsidian Sync Rules]]를 본다.
- 템플릿 작성·배치·엔진·파일명은 [[15. Templates]]를 따른다.

## Caveats

- **파일 번호는 우선순위가 아니다.**
	- 이 문서와 [[15. Templates]]는 같은 4단계 운영 계층이다.
	- `04`와 `15`는 폴더 안 이름 충돌을 피하기 위한 번호일 뿐, 어느 쪽이 위라는 뜻이 아니다.
	- 폴더·속성·권한 계약과 충돌하면 양보한다.

- **설정 키는 채택자 환경에서 확인한다.**
	- 문서에 적힌 값을 현재 검증된 런타임 상태로 쓰지 않는다.

- **ZotLit 파일 이동은 조용히 깨진다.**
	- Zotero/ZotLit 관리 노트를 Obsidian 안에서 임의로 이동하면 에러 없이 링크가 끊어질 수 있다.
	- 이동 전 `zotero`/`zt-attachments` property 존속 여부를 확인한다.
	- 플러그인 디렉터리는 manifest의 `id`(`zotlit`)로 확인한다.

- **Periodic Notes는 설치 전제로 쓰지 않는다.**
	- `auto/` 폴더를 설치 증거로 쓰지 않는다.

- **미문서화 플러그인 설정 경로를 하드코딩하지 않는다.**
	- 플러그인 설정 파일의 정확한 경로가 항상 예측 가능하지는 않다.
	- 경로를 코드/문서에 하드코딩하기 전에 실제 `.obsidian/plugins/` 트리를 확인한다.
	- 값 본문(토큰·계정)은 문서에 복사하지 않는다.

- **역할 구분과 실제 운영 절차를 나눈다.**
	- 동기화·버전 관리·백업의 역할 구분은 이 문서가 담당한다.
	- 구체적인 동기화·백업 인프라 운영은 이 템플릿 범위 밖이며 채택자의 인프라 노트에 둔다.
	- DEVONthink 세부 운영은 [[12. DEVONthink Guideline]]을 따른다.
	- Agent authority와 workflow selection은 [[03. Agent Permissions and Workflows]]를 따른다.
	- 개인 authored-note의 문장 구성·Markdown 표현은 [[05. Writing Style]]을 따른다.
	- 노트 배치·속성·권한은 [[01. Folders and Placement]], [[02. Properties]], [[03. Agent Permissions and Workflows]]를 따른다.

### Commit Evidence Self-reference

- **같은 commit 안에 그 commit의 최종 hash를 자기 참조로 넣을 수 없다.**
	- 최종 작업 commit URL 하나를 후속 보고서 저장 commit에 기록한다.
	- 보고서의 증거 링크만 저장하는 commit은 새 작업 commit으로 취급하지 않는다.
	- 완료 응답에는 그 evidence commit의 full SHA와 immutable URL을 반환한다.
	- 보고서를 자기 자신의 hash로 끝없이 갱신하지 않는다.

### Independent Backup Histories

- **주 작업 vault와 보조 vault는 서로 독립된 Git history를 유지한다.**
	- 각 satellite vault·machine·repository의 source metadata는 해당 작업 사본에서 생성된 보고서에 남긴다.
	- Obsidian Sync로 content가 수렴할 수 있지만, 수신 machine은 source가 아니며 backup commit은 authorship의 근거가 아니다.
	- cross-repository pull·merge·reset을 하지 않으며, Git push를 Obsidian Sync 완료의 증거로 기록하지 않는다.

### DEVONthink PARA Exception

- **DEVONthink의 PARA 1-depth는 예외다.**
	- Do-NOT-mirror 규칙을 DEVONthink의 `10 Projects/20 Areas/30 Resources/40 Archives` 구조에 잘못 적용해 규칙 위반으로 오판하지 않는다.
	- 이는 DEVONthink 고유 표준이지 Obsidian 패턴의 모방이 아니다.
	- 상세는 [[12. DEVONthink Guideline]]을 본다.

### Agent Commit Failures

- 현재 저장소·branch·remote나 실행 런타임을 확인하지 못하면 추정해서 커밋하지 않는다.
	- 확인이 필요한 항목을 보고한다.
- signing·hook·파일시스템 권한 문제로 커밋이 실패하면 원인을 보고한다.
	- 검증이나 서명 설정을 우회하지 않는다.
	- 파일이 저장됐는지와 Git에 기록됐는지를 구분한다.
	- 미커밋 변경은 보존하며 버전 기록 완료로 보고하지 않는다.
