## Overview

이 문서는 노트의 물리 위치만 정한다. 파일 트리에서 무엇을 어디에 둘지, 최상위 폴더와 하위 칸의 이름 규칙을 담당한다.

- **다루는 것**
	- 실제 폴더 구조와 이름
	- 새 노트를 둘 위치와 이동 기준
- **다루지 않는 것**
	- 속성의 기록 방식은 [[02. Properties]], 노트 사이 관계는 [[16. MOC]]가 담당한다.
	- 권한과 knowledge-work workflow/skill 선택은 [[03. Agent Permissions and Workflows]], 애플리케이션 역할·인터페이스·통합 정책은 [[04. Applications and Integrations]], 템플릿은 [[15. Templates]]를 따른다.

작성 틀은 [[guideline.template]]을 따른다.

```text
Folders and Placement
├── 책임 구분 — Folder · Properties · MOC
├── Naming Pattern — NN. Name(최상위) / NN Name(하위), semantic name(item)
├── Folder Structure — 12개 최상위 taxonomy (00~90)
├── Placement Rules — 폴더별 배치 기준
├── Agent Work Record Placement
├── Note Placement Decision Tree — 14단계 신규 노트 배치 판정
├── Guideline File Numbering — Policy 4 tiers / Writing Style / Operational Guidelines
├── MOC 파일 위치 — 70. Collections/03 MoC/ (관계 규칙은 [[16. MOC]])
└── taxonomy.json Cross-ref — folder intent/concept/agentWritable 매핑
```

## Map

### 책임 구분

볼트의 축은 셋이다. 같은 규칙을 두 문서에 정의하지 않는다.

| 축 | 담당 | 하는 일 | 하지 않는 일 |
| --- | --- | --- | --- |
| Folder | 이 문서 | 파일 트리의 물리 위치, 폴더 이름, MOC 노트가 사는 칸 | 지식 관계, 필드 값 |
| Properties | [[02. Properties]] | frontmatter 직렬화. `tags`와 `moc` 필드의 이름·자료형·허용 기록 방식 | 폴더 칸, 어떤 관계를 고를지 |
| MOC | [[16. MOC]] | 노트를 통해 맺는 관계, 맥락, 탐색, 멤버십·Tier·dual-axis | 파일을 옮기거나 복사하는 분류 |

- **MOC 멤버십은 폴더를 가로지를 수 있다.**
	- 같은 지도에 있어도 노트를 옮기거나 복제하지 않는다.
	- 관계·선택 규칙은 [[16. MOC]]만 따른다.

### Naming Pattern

- 최상위 폴더는 이 문서에 정의된 고정 numeric ID(`NN. Name`)를 사용한다.
- 고정 taxonomy layer에만 `NN. Name` 형식을 사용한다. 하위 폴더는 `NN Name`(마침표 없음, 예: `01 Guideline`, `02 Templates`)을 사용한다.
- project / area / archive item, year folder, supporting folder는 semantic name을 사용한다.
- 숫자의 의미는 parent taxonomy 안에서 해석한다. `15. Work/01 Project`와 `10. Time/01 Daily Notes`는 서로 다른 namespace다. bare number(`11`, `12`, `13` 등)를 path 없이 해석하지 않는다.
- 노트는 가장 구체적인 유효 home에 둔다. 최하위 폴더에만 노트를 배치한다 (inbox 제외).
- `15. Work/01 Project/<name>/`과 `15. Work/02 Area/<name>/`는 예외적으로 folder root에 hub note(`<name>.md`)를 둘 수 있다. 이 두 taxonomy 하위 item folder에는 numeric prefix를 붙이지 않는다.

### Agent Work Record Placement

- Human work records use the existing Inbox destinations below.
	- The destination table does not create a new folder taxonomy.
	- Do not create folders or move records to satisfy this route.

| Destination | Use |
|---|---|
| `00. Inbox/02 Claude Code/` | Work records for the Claude Code runtime identity |
| `00. Inbox/03 Codex/` | Work records for the Codex runtime identity |
| `00. Inbox/04 GJC/` | Work records for the GJC runtime identity |
| `00. Inbox/05 Aside/` | Work records for the Aside runtime identity |

- Optional runtimes without a shipped Inbox destination (for example Hermes) have no human-facing Inbox route.
	- When a destination is unresolved, ask the user before creating a human work record.
	- Do not invent a folder to resolve identity or placement.
	- Do not replace a human work record with runtime memory.
- Human work records are readable Markdown notes.
	- Runtime memory and machine receipts are machine state and do not satisfy this route.
	- Use [[03. Agent Permissions and Workflows#Agent Work Records]] for the record contract.
	- Use [[02. Properties]] for metadata and [[05. Writing Style]] for prose.
- Use the filename pattern `YYYY-MM-DD HHmm <agent> - <Session Topic>.md`.
	- There is no hyphen between `HHmm` and the lowercase, filesystem-safe runtime label.
	- Use the first report's timestamp and path for every update in that session.
	- Resolve the session's existing report through [[03. Agent Permissions and Workflows#Agent Work Records]].
	- Append a filesystem-safe uniqueness suffix only when the exact path collides; the suffix is not a session identifier.
	- Never fabricate a session identifier.

### Note Placement Decision Tree

새 note가 생기면 순서대로 위치를 결정한다:

1. 아직 분류가 끝나지 않았는가? → `00. Inbox`
2. periodic planning/review/roundup note 인가? → `10. Time`
3. end condition 이 있는 active work 인가? → `15. Work/01 Project`
4. ongoing responsibility 인가? → `15. Work/02 Area`
5. inactive completed/stopped item 인가? → `15. Work/03 Archive`
6. 생각 노트를 한 번 더 정제한 발행본인가? → `25. Digital Garden` (원본 생각 노트는 `40. Permanent Notes` 에 잔류한다 — 복사본이 아니다)
7. external source 에서 출발한 thought 인가? → `30. Literature Notes`
8. 독립적 evergreen insight 인가? → `40. Permanent Notes`
9. AI-specific artifact(Wiki 합성, 용어, roundup 등) 인가? → `50. AI`. 단, 특정 프로젝트 맥락에서 나오는 AI 생산물은 `15. Work` 소속이 우선이며 작성 주체는 `authorship` 으로 구분한다 (skill package 는 제외 — vault 밖 GitHub repo 관리, [[03. Agent Permissions and Workflows]] 참고)
10. faith/spiritual note 인가? → `60. Saint`
11. 사람·장소·조직·발행 채널·prompt·MOC·꽃 카드 또는 저장 이유가 확인된 reusable software/tool object 인가? → `70. Collections` (`09 Channel`, `type: channel`; `08 Github`, `type: tool`; `10 Flowers`, `type: flower`). MOC 노트 파일은 `03 MoC/`에 둔다. 어떤 노트를 어느 지도에 연결할지는 [[16. MOC]]
12. book, paper, user-curated image 같은 reference artifact 인가? → `80. References`; 자동/unreviewed GitHub capture는 `85. Raw/03 Github`
13. 사람이든 에이전트이든 수집한 원문인가? → `85. Raw`
14. vault setting, guideline, template, home, index, base, 운용 규칙, 결정 기록, Excalidraw drawing·plugin asset 인가? → `90. Settings` (drawing·asset 은 `07 Excalidraw/`; 특정 프로젝트의 결정은 해당 `15. Work` 폴더에 둔다)

#### Guideline 유지 원칙 — MECE

**Guideline은 책임이 서로 겹치지 않고, 필요한 영역이 빠지지 않게 구성한다.**

- 규칙의 담당과 참조는 [[00. Guideline Authoring#Rule Ownership|규칙의 담당과 참조]]를 따른다.
	- 위 책임표에 없는 규칙은 그 절로 확인한다.
- 현행 규칙의 정비는 [[00. Guideline Authoring#Current Rules|현행 규칙의 정비]]를 따른다.

### MOC 파일 위치

- **MOC 노트 파일은 `70. Collections/03 MoC/`에 둔다.**
	- 하위 폴더를 만들지 않는다. 번호로 정렬하므로 flat이다.
	- 번호 없는 파일을 이 칸에 두지 않는다. 발견하면 번호와 부모 연결은 [[16. MOC]]를 따른다.
- **이 칸은 파일 자리다.**
	- Tier, dual-axis, 멤버십, 선택 한도는 [[16. MOC]]가 담당한다.
	- `moc` 필드를 어떻게 적는지는 [[02. Properties]]가 담당한다.

### taxonomy.json Cross-ref

`.oms/taxonomy.json` 은 이 Policy 의 폴더 배치 원칙을 기계가 읽을 수 있는 형태로 투영한 것이다 — 12개 최상위 폴더 각각의 `intent`(1행 설명), `concept`(대응 `.oms/concepts/<concept>.yaml` 파일명), 그리고 `agentWritable: true` 플래그(에이전트 쓰기 허용 여부)를 정의한다. `agentWritable: true` 는 `00. Inbox`, `15. Work`, `50. AI`, `85. Raw` 4개 폴더에만 명시되어 있으며, 이는 [[03. Agent Permissions and Workflows]]의 Zone 판정표와 정합해야 한다.

- `10. Time`의 하위 폴더별 권한은 최상위 flag만으로 판정하지 않는다.
	- 표현 한계는 [[#Time Subfolder Granularity]]를 확인한다.

## Rules

- 최상위 폴더의 고정 numeric ID를 임의로 변경하지 않는다. 변경 시 이 문서를 먼저 갱신한다.
- 노트는 가장 구체적인 유효 home에, 최하위 폴더에만 둔다(inbox 제외).
- `15. Work/` 하위 item folder에는 numeric prefix를 붙이지 않는다.
- folder path 변경 시 templates, Bases, skills, query, direct path link를 같은 변경 배치에서 함께 갱신한다.
- MOC 노트 파일은 `70. Collections/03 MoC/`의 flat 구조를 지킨다.
- 관계·멤버십·Tier는 [[16. MOC]]를 따른다. 이 문서는 파일 위치만 정한다.

## Caveats

- **폴더 배치가 충돌하면 이 문서의 기준을 따른다.**
	- 운영 정책의 우선순위는 폴더 → 속성 → 권한 → 애플리케이션·통합과 템플릿의 4계층이다.
	- 애플리케이션·통합과 템플릿은 서로 다른 책임을 가진 같은 계층이다.
	- MOC는 독립된 관계 축이며, Writing Style은 본문 표현을 담당한다. 파일명 번호가 새 우선순위를 만들지 않는다.

### Bare Number 해석 금지

`11`, `12`, `13` 같은 숫자는 path 없이 해석하지 않는다. root number와 child taxonomy number는 서로 다른 namespace다.

### Time Subfolder Granularity

- `.oms/taxonomy.json`은 하위 폴더별 쓰기 범위를 표현하지 못한다.
	- `10. Time` 전체의 false 값이 모든 하위 폴더에 동일한 권한을 뜻하지 않는다.
	- 실제 쓰기 범위는 [[03. Agent Permissions and Workflows#Zone Determination Table]]을 따른다.
- 이 문서는 스키마의 표현 한계를 기록한다.
	- taxonomy 스키마 변경은 별도 작업이며, 이 설명만으로 기계적 강제가 구현되지는 않는다.

### Folder Move의 연쇄 영향

folder path 변경은 guideline만의 문제가 아니다. templates, Bases, skills, query, direct path link를 같은 변경 배치에서 함께 갱신한다.

### MOC로 폴더를 재배치하지 않기

노트가 어떤 지도에 속하는지와 파일이 어느 폴더에 있는지는 별개다. 멤버십 때문에 옮기거나 복사하지 않는다. 선택 규칙과 주의 예는 [[16. MOC]]를 본다.

### Trash Path

`.trash/`는 canonical structure 판단에 포함하지 않는다.
