## Overview

가이드라인을 만들거나 수정할 때는 이 문서를 읽고 [[guideline.template]]을 사용한다.

- **다루는 것**
	- 가이드라인의 범위·담당·이름·본문 구성과 갱신 방법
- **다루지 않는 것**
	- 개별 규칙·스키마·권한은 각각의 담당 문서가 정의한다.
	- 이 문서는 새로운 분류 축이나 정책 우선순위를 만들지 않는다.

```text
Guideline Authoring
├── 적용 범위 — 볼트 운영 규칙
├── Rule Ownership — 하나의 규칙과 하나의 담당 문서
├── From Concepts to Rules — 검증한 전문 개념을 실행·검토 기준으로 구체화
├── Current Rules — 지금 적용할 정본만 유지
├── Naming Convention — 역할을 설명하는 영어 파일명
├── 작성 준비 — 템플릿과 인덱스 연결
├── 본문 구성 — 섹션별 MECE와 중첩 목록
└── 검토 — 규칙 중복과 참조 확인
```

## Map

- **가이드라인은 이 Obsidian 볼트를 운영하는 규칙으로 한정한다.**
	- 노트의 배치·속성·연결·작성, 편집 권한, 템플릿·도구 설정처럼 볼트의 동작과 일관성을 정하는 내용을 다룬다.
	- 일반적인 생산성 조언, 시간 관리 철학, 생활 습관은 가이드라인으로 두지 않는다.
		- 관련 지식과 개인 실천 기록은 내용과 소유 맥락에 맞는 노트에 둔다.
		- 볼트 사용에 꼭 필요한 절차는 해당 규칙의 담당 문서에서 다룬다.
	- 생산성 문서에 볼트 운영 규칙이 섞여 있으면 규칙과 조언을 분리한다.
		- 속성 정의는 [[02. Properties]], 배치는 [[01. Folders and Placement]]로 연결한다.
		- 문서 전체를 생산성이라는 이유로 볼트 정책으로 취급하지 않는다.

### Rule Ownership

- **책임을 먼저 정한다.**
	- 볼트의 분류 축은 Folder, Properties, MOC로 구분한다.
		- Folder는 노트의 물리적 배치를 다룬다. 담당은 [[01. Folders and Placement]]다.
		- Properties는 노트의 속성을 다룬다. Tag는 Properties의 한 항목이며 별도의 분류 축으로 두지 않는다. 담당은 [[02. Properties]]다.
		- MOC는 노트를 통한 지식 관계와 탐색을 다룬다. 폴더 위치와 같은 책임이 아니며, 노트가 어느 폴더에 있든 관계를 건넌다. 소속·선택·Tier 규칙은 [[16. MOC]]만 담당한다.
	- 문서 첫머리에 해결할 질문과 다루지 않을 범위를 적는다.
	- 기존 규칙은 [[01. Folders and Placement#90/01 내부 구조 (Guideline File Numbering)|담당 문서 표]]에서 찾는다.
	- 이 문서는 작성 방법을 정한다. 분류 축을 추가하거나 기존 정책의 우선순위를 변경하지 않는다.
- **규칙은 하나의 담당 문서에서만 정의한다.**
	- 다른 문서에 같은 정의·허용값·조건·예외를 옮겨 적지 않는다.
	- 필요한 문맥에서는 [[05. Writing Style#Links & Evidence|노트·헤딩·문장 별칭 링크]]로 정본을 참조한다.
	- 설명을 짧게 요약했다는 이유로 또 하나의 규칙 사본을 만들지 않는다.
- **새 규칙은 기존 담당 문서에 반영한다.**
	- 문서마다 다루는 범위와 다루지 않는 범위를 구분한다.
	- 담당이 없는 독립적인 책임이 확인될 때만 새 문서를 만든다.
- 루트 `AGENTS.md`는 작업 조건에서 담당 정본으로 연결하는 진입점으로 유지한다.
	- 시작 순서와 조건별 필수 읽기 경로를 적는다.
	- Guideline의 정의·상세 규칙·명령 목록을 복사하지 않는다.
	- 정본에 없는 유효 규칙은 담당 Guideline으로 옮긴 뒤 참조로 대체한다.
- **구조 변경과 참조 갱신은 한 작업이다.**
	- 통합·분리·개명 시 관련 노트·인덱스·템플릿·`AGENTS.md`의 참조를 함께 확인한다.
	- 본문 정의만 옮기고 기존 문서에 같은 규칙을 남겨 두지 않는다.

### From Concepts to Rules

- 사용자의 의도를 해당 분야의 전문 개념으로 해석하고, 실행할 규칙으로 구체화한다.
	- 대화에서 반복되는 목적·선호·문제 사례를 읽고, 이를 설명하는 실제 jargon과 원칙을 찾는다.
	- 용어의 의미와 출처 확인은 [[05. Writing Style#Links & Evidence|전문 용어 검증·연결 규칙]]을 따른다.
	- 출처에서 확인한 개념과 볼트에 적용할 규칙을 구분한다. 용어의 실재 여부와 사용자의 요구에 맞는지는 각각 판단한다.
- 규칙에는 적용 조건, 행동, 검토 기준을 적는다.
	- `정확하게 써라`처럼 평가하기 어려운 지시는 무엇을 확인하고 어떻게 수정할지로 풀어 쓴다.
	- 전문 용어 뒤에는 그 개념이 실제 작성·편집에서 요구하는 행동을 붙인다.
	- 예를 들어 `용어 일관성`을 적용한다면, 같은 개념의 명칭을 대조하고 의미 차이가 없는 변형을 정리하는 절차로 쓴다. 용어 선택과 표기의 정본은 Writing Style에 둔다.
- 규칙을 지켰는지 실제 문장이나 작업 결과로 확인할 수 있게 쓴다.
	- 원문과 수정문, 적용 사례, 점검 항목 중 적합한 방법으로 판단 기준을 보여 준다.
	- 규칙을 읽은 사람이 같은 사례에서 무엇을 해야 하는지 정할 수 있는지 검토한다.

### Current Rules

- **가이드라인에는 지금 적용할 정본만 남긴다.**
	- 폐기된 규칙, 완료된 전환 과정, 과거 문서의 흡수 경위를 현행 규칙과 함께 나열하지 않는다.
	- 바뀐 규칙은 현재 문장으로 교체한다. 이전 문장에 취소선을 그어 보관하지 않는다.
	- 이전 내용과 변경 이유는 [[04. Applications and Integrations#Git and GitHub|Git 버전 이력]]에서 확인한다.
- **현재 문서만 읽어도 판단하고 갱신할 수 있게 쓴다.**
	- 적용 대상·조건·예외를 현재형으로 명확히 적는다.
	- “예전에는”, “이제는”, “이관 후” 같은 전환 설명을 알아야 규칙을 해석할 수 있게 만들지 않는다.
- **참조는 실제로 존재하는 정본과 헤딩을 가리킨다.**
	- 없어진 노트는 현행 근거로 사용하지 않는다. 실제 담당 문서로 연결을 고치거나 불필요한 참조를 제거한다.
	- 링크를 맞추려고 빈 노트·가짜 별칭·중복 안내 문서를 만들지 않는다.
	- 표기와 문장 내 연결 방법은 [[05. Writing Style#Links & Evidence]]를 따른다.

### Naming Convention

- **파일명은 담당 역할을 드러내는 짧은 영어 명사구로 쓴다.**
	- 단어는 공백으로 구분하고 주요 단어의 첫 글자는 대문자로 쓴다.
	- [[00. Guideline Authoring]], [[05. Writing Style]], [[02. Properties]]처럼 문서를 열기 전에도 책임을 알 수 있게 이름 짓는다.
	- `Guideline` 폴더가 문서 성격을 알려 주므로 `Guideline`·`Policy`를 접미사로 반복하지 않는다.
	- 한국어 이름이나 검색용 표현은 `aliases`에 기록한다.
- **가이드라인 파일명에는 두 자리 번호를 붙인다.**
	- `NN. Name.md` 형식을 사용하고 같은 폴더에서 기존 번호와 충돌하지 않는지 확인한다.
	- 가이드라인 작성 규칙은 `00`에 두고, 개별 가이드라인은 그 뒤에 배치한다.
	- 번호 자체로 정책 우선순위를 추론하지 않는다. `15`, `16`도 새 계층이나 새 권한이 아니다.
- **이름을 바꿀 때는 연결도 함께 갱신한다.**
	- 책임이 같은 문서를 다른 이름으로 새로 만들지 않는다.
	- 개명 시 인덱스·템플릿·규칙 문서의 참조를 확인한다. 이름 규칙을 추가했다는 이유로 기존 파일을 일괄 개명하지 않는다.

### Template and Structure

- **템플릿을 적용하고 필요한 연결을 남긴다.**
	- 새 가이드라인은 [[guideline.template]]을 읽고 그 틀에서 시작한다.
	- frontmatter에는 `index: "[[🏷 Guideline]]"`를 기록한다.
		- 인덱스는 가이드라인을 찾는 입구다. MOC나 Tag로 이 연결을 대체하지 않는다.
		- 나머지 속성과 provenance는 [[02. Properties]]를 따른다.
	- 본문에 사용한 템플릿 링크를 남긴다.
		- 사람의 탐색용 노트 연결은 [[05. Writing Style#Links & Evidence]]를 따른다.
		- 에이전트 필수 읽기 표기는 [[03. Agent Permissions and Workflows#Context Discovery]]를 따른다.
	- 템플릿의 안내 문구는 실제 내용으로 바꾸고, 미완성 예시나 빈 섹션을 완성본에 남기지 않는다.

- **큰 틀은 유지하고 섹션 안은 자유롭게 구성한다.**
	- 템플릿의 `## Overview`, `## Map`, `## Rules`, `## Caveats`를 사용한다.
		- Overview에는 목적과 범위를 쓴다.
		- Map에는 주제별 규칙을 배치한다.
		- Rules에는 적용·검토 기준을 쓴다. Map의 상세 규칙을 그대로 반복하지 않는다.
		- Caveats에는 적용 경계와 주의할 오해를 쓴다.
			- 예외와 알려진 gap의 배치는 [[#Exceptions and Known Gaps]]를 따른다.
	- 각 `##` 내부는 내용에 맞게 구성하되, 항목끼리 겹치지 않고 필요한 내용이 빠지지 않게 한다.
	- 가독성은 [[05. Writing Style#Semantic Grouping|핵심과 부연을 묶는 목록·문단 구성]]을 따른다.
	- 들여쓰기는 [[05. Writing Style#Emphasis & Syntax|본문 중첩 목록 표기]]를 따른다.

### Exceptions and Known Gaps

- 예외와 알려진 제약의 상세 설명은 해당 가이드라인의 `## Caveats` 아래에 모은다.
	- 각 항목에 내용을 식별할 수 있는 고유한 하위 heading을 둔다.
	- 여러 가이드라인의 예외를 별도 문서 한 곳으로 옮기지 않는다.
- 본문에는 정상 규칙과 예외가 적용되는 조건을 남긴다.
	- 상세 설명은 `[[#해당 heading]]`으로 연결한다.
	- 같은 예외 설명을 본문과 Caveats에 복제하지 않는다.
	- 권한 경계와 즉시 알아야 하는 안전 조건은 참조를 따라가기 전에도 식별할 수 있게 유지한다.
- 알려진 gap에는 영향을 받는 조건과 실제 보장되지 않는 동작을 적는다.
	- 다른 문서가 담당하는 규칙은 그 담당 문서로 연결한다.
	- 일반적인 분기 조건, 스키마 정의, 예시를 예외라는 이유로 본문에서 분리하지 않는다.
- 예외를 옮길 때는 해당 heading으로 연결된 참조를 함께 확인한다.
	- 링크를 따라가면 한 곳에서 현재 조건과 한계를 읽을 수 있어야 한다.

### AGENTS Authoring

- **Use AGENTS files as routing contracts, not as policy copies.**
	- A root contract owns the repository purpose, recognized agent identities, identity confirmation boundary, and entry routes.
	- Keep canonical detailed policy in its owning guideline and link to it instead of copying definitions, mutable rosters, catalogs, or path inventories.
	- A nested contract inherits the root contract and records only its local scope, context, rules, routes, and verification.
- **Keep folder-specific requirements in Local Rules.**
	- State the applicable paths, whether descendants are included, the trigger, and the required action.
	- Keep domain context in `Local Context`, reading pointers in `Local Routes`, and acceptance checks in `Local Verification`.
	- Reference inherited rules instead of copying them.
	- Local rules must remain within canonical permission and protected-content boundaries.
	- Move a rule that applies vault-wide to its canonical guideline instead of repeating it across nested contracts.
- **Load the matching frame before authoring a contract.**
	- Use [[root-agents.template]] for a repository-root contract.
		- Agents must read `90. Settings/02 Templates/agent/root-agents.template.md` before rendering or revising a root contract.
	- Use [[nested-agents.template]] for a nested contract.
		- Agents must read `90. Settings/02 Templates/agent/nested-agents.template.md` before rendering or revising a nested contract.
		- Existing shipped nested contracts may keep the legacy Project Overview frame; new nested contracts use [[nested-agents.template]].
	- Use [[work-record.template]] for a human-facing agent result summary.
		- Agents must read `90. Settings/02 Templates/agent/work-record.template.md`; [[agent-session.template]] remains the machine-ingest receipt.
	- Resolve metadata from [[02. Properties]] and preserve valid metadata already present on an edited contract.
- **Require independent lanes for AGENTS contract changes.**
	- For AGENTS creation, substantial regeneration, or structural or contract changes, delegate scoped, read-only investigations to multiple canonical planner or architect agents independent of the author.
		- Use the runtime's task delegation tool and run independent areas in parallel when available.
	- Require each lane to return concrete path or heading evidence, the canonical owner, and unresolved gaps.
	- The author synthesizes one owner-consistent contract from those findings within the user's authorized scope.
	- Scale the number of investigators to the relevant independent areas instead of imposing a fixed count on every task.
- **Review the resulting changes independently.**
	- After the author writes, an author-independent architect or critic reviews the result for MECE ownership, omissions, conflicts, stale or missing references, and requirement coverage.
	- Fix every finding and repeat the independent review before completion.
	- If the runtime cannot provide delegation, disclose which independent discovery or review stages were unavailable.
		- Do not present a local self-check as equivalent to either stage.
	- A minor typo or single-pointer correction may use a focused local check instead of the full lanes.
- **Verify the rendered contract and its failure cases.**
	- Check the destination path, required headings, owner links, provenance, and resolved template output.
	- Check unknown identity and missing destination scenarios explicitly and record them as unresolved or not checked rather than fabricating a value.
	- Report unavailable checks honestly; do not add fake build commands or runtime deployment claims.
- **Use English contract headings and template instructions.**
	- Follow [[05. Writing Style#Semantic Grouping|semantic grouping]] and [[05. Writing Style#Emphasis & Syntax|Markdown syntax]] instead of duplicating those style rules here.

## Rules

- 저장 전에 템플릿 적용, Guideline 인덱스, 관련 문서 링크를 확인한다.
- 각 규칙의 담당 문서가 하나인지 확인한다.
	- 다른 문서의 규칙은 복사하지 않고 해당 문서나 섹션으로 연결한다.
- 섹션 사이의 중복과 필요한 조건·예외의 누락을 검토한다.
- 전문 개념의 출처, 사용자 의도와의 관계, 적용 조건·행동·검토 기준을 확인한다.
- 링크 대상이 실제로 존재하는지, 템플릿 안내 문구가 남지 않았는지 확인한다.
- 담당 문서 밖에 복사된 정의나 폐기 문장이 남아 있지 않은지 확인한다.
- 이 검토는 수동으로 수행한다. 자동 검사나 플러그인이 강제한다고 가정하지 않는다.

## Caveats

- 기기 간 동기화·백업 운영은 [[04. Applications and Integrations]]를 따른다. 이 문서가 동기화 수단을 정의하지 않는다.
- 원격 미디어 표시는 [[05. Writing Style#Links & Evidence]]를 따른다.
- 이 문서의 작성 규칙만으로 기존 노트 전체를 일괄 재작성하지 않는다.
	- 승인된 생성·수정 범위에 적용한다.
- 템플릿 사용은 플러그인 설정 변경을 뜻하지 않는다.
	- 템플릿 엔진과 배치 계약은 [[15. Templates]]를 따른다.
- 가이드라인을 작성한다는 이유로 편집 권한을 확대하지 않는다.
	- 권한과 보호된 본문은 [[03. Agent Permissions and Workflows]]를 따른다.
